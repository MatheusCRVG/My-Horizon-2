# Incremental encrypted sync

`index.ts` exports `createOperations`, `syncVault`, `createRpcTransport` and `retryWithBackoff` plus their interfaces. The engine has no Zustand or Supabase dependency.

- Before a local write, call `createOperations(previous, next, keys, owner)` once and atomically persist its returned operations with the encrypted next document. An operation batches changed entities, tombstones and relevant conflicts. Initial migration can compare an empty document to the legacy document.
- Call `syncVault` under the same owner lock used for edits and account/session metadata. The repository `commit` must atomically store the encrypted vault/cursor, enqueue operations and remove acknowledged operation IDs. Do not implement `commit` as independent writes.
- An operation keeps its UUID and encrypted payload across retries. ACK happens only when that exact UUID/payload is observed in a validated remote page. A timeout or failed local commit keeps the operation available for replay.
- `accountId` is the authenticated Supabase UUID. `owner` remains the original cryptographic owner, including a legacy Google subject. Both the account binding and the vault/header binding must pass. `active()` must check the session epoch and the current authenticated account.
- `bootstrap()` accepts a header or `{header, vault_id, ...}`. It returns only the validated header. Reconstruct the document with an encrypted empty local document and `syncVault` at cursor zero; bootstrap preview operations never advance the cursor.
- A new empty vault may have `pending=true` and no operations: exchange creates its remote header. A nonempty pending document without an outbox is an error requiring explicit queue repair, never a reason to mark data as synced.
- Header key-wrapping changes require reopening/explicit migration. They are not silently accepted while syncing with an older unlocked header.
- Uploads contain at most 20 operations and stay below 16 MiB measured as PostgreSQL JSONB UTF-8, with 16 KiB reserved for RPC/header overhead. Returned pages contain at most 100 operations and 16 MiB of payloads. Each ciphertext is capped at 8 MiB of base64 text.
- Large edits/migrations are partitioned before encryption. Changed goals, their linked contributions/transactions, and relevant conflicts remain in the same operation. An individual entity or related group exceeding the limit raises an explicit error. All returned operations must be committed locally together. Independent groups may be checkpointed on different remote pages; the engine returns the final document only after all pages are consumed.
- The RPC adapter automatically retries network/timeout and status 0/5xx failures up to three attempts with short exponential jitter. It reuses the original request and never regenerates UUID/ciphertext. Authorization, validation, rate-limit and protocol failures are surfaced immediately. Pass the session/account `active()` guard to both the adapter and engine.

RPC contract: `horizon_exchange(p_vault_id, p_header, p_operations, p_cursor, p_limit)` returns `{header, operations:[{op_id, seq, payload}], cursor, has_more}`. The cursor must be the last returned sequence, or the unchanged requested cursor for an empty page. The SQL implementation allocates contiguous sequences per user, so the client rejects skipped sequence numbers as well as reordered/duplicate rows. The backend must enforce account access and stable operation UUID deduplication.
